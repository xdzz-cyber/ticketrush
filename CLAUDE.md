# TicketRush — контекст проєкту

Командний іспитовий проєкт: розподілена система продажу квитків з піковим навантаженням (flash sale).
Тема погоджена викладачем. Здача: **10.12.2026**. На іспиті кожен член команди презентує **свою** частину,
тому межі відповідальності в коді мають бути чіткими.

Команда:
- **Габрук Богдан** — Booking API, бронювання в Redis, публікація подій, spike-тест.
- **Астахов Богдан** — Order Worker, Nginx, Docker Compose (масштабування), load-тест і тест 1 vs 3 інстанси.

Оцінюється не складність, а робочий прототип, архітектура, навантажувальне тестування й опис результатів.
**Не ускладнювати**: без зайвих шарів, патернів і сервісів понад описані нижче.

## Архітектура

```
Клієнти / k6 → Nginx → Booking API ×3 ─┬→ Redis      (каталог, залишок місць, TTL броней)
                                       └→ RabbitMQ   (підтверджені бронювання)
                                              ↓
                                         Order Worker ─┬→ PostgreSQL (події, замовлення)
                                                       └→ Redis      (звільнення прострочених броней)
```

- **Booking API** (.NET 8, ASP.NET Core Minimal API), stateless, запускається у кількох інстансах.
  - каталог подій з кешем у Redis;
  - бронювання місця — **атомарно** одним Lua-скриптом у Redis (перевірка залишку + декремент + запис броні з TTL ~5 хв);
  - підтвердження бронювання → публікація повідомлення в RabbitMQ;
  - ідемпотентність запитів (ключ ідемпотентності від клієнта).
- **Order Worker** (.NET 8 Worker Service): споживає чергу, імітує оплату, пише замовлення в PostgreSQL (EF Core),
  повертає місця з прострочених броней у продаж. Обробники повідомлень ідемпотентні.
- **Shared**: контракти повідомлень між сервісами. Змінювати лише за згодою обох.
- **Інфраструктура**: Docker Compose (redis, rabbitmq, postgres, nginx, booking-api, order-worker).

## Цілі навантажувального тестування (k6)

| Метрика | Ціль |
| --- | --- |
| Пропускна здатність бронювання | ≥ 500 запитів/с |
| Затримка бронювання | p95 ≤ 300 мс |
| Oversell (продано понад ліміт) | 0 |
| Помилки 5xx під номінальним навантаженням | < 1% |
| Масштабування | приріст RPS при переході з 1 на 3 інстанси Booking API |

Сценарії: **load**, **spike** (flash sale на одну подію з обмеженою кількістю місць), **scaling** (1 vs 3 інстанси).
Графіки для звіту — з вбудованого веб-дашборду k6.

## Правила роботи

- Перед великими змінами — коротко запропонувати план і дочекатися підтвердження.
- Після змін — зібрати (`dotnet build`) і, де можливо, запустити тести / `docker compose up`.
- Конфігурація через `appsettings.json` + змінні середовища з docker-compose; без секретів у репозиторії.
- README має містити: як запустити систему, як запустити кожен k6-сценарій, де дивитися результати.
- Коміти маленькі, з повідомленнями англійською; кожен комітить свою частину сам (для прозорості внеску).
